#+TITLE: S6 exact Windows runtime HP1 latency diagnosis
#+DATE: 2026-10-10

* Result and ownership
The transport does not have a 150--300 ms fixed floor. On the supplied image,
an unparsed one-byte echo with no newline and no EOF has median 0.0423 ms,
maximum 0.1695 ms. The red HP1 distribution consists of expensive interpreted
string/regexp work plus synchronous mid-form collection pauses. The decision
cond itself is cheap. No NeLisp runtime file was modified.

Each diagnostic process is launched suspended, assigned to an anonymous
kill-on-close Job Object, resumed, and waited before launching another.
No engine host, TSF client, registry write or public endpoint is used.

The in-repo fix replaces HP1 regexp splitting/validation with a bounded ASCII
scan in engine/host-policy.el, preserving decimal conversion, copied reply
IDs (including leading zeros), kind/context validation, partial/batched frames,
4096-character frame and 2048-character context limits, and private pause hooks.
The pause-kind comparison still uses its raw original decimal spelling.
It does not disable GC, adjust memory/latency thresholds, or change decisions.

* Clock split and causal collector control
The diagnostic records float-time immediately before read, after read,
before response write and after write. Python records time.time at send and
raw os.read arrival, plus perf_counter for roundtrip and send durations.
Python does not wait for a newline: it consumes the known response byte count.
The timing record is emitted AFTER the response and is excluded from response
roundtrip. Its cost can affect the next read-wakeup interval, so raw echo and
uninstrumented host-windows-s6.py remain the transport/budget references.

This image's float-time has approximately millisecond granularity. Sub-ms
cross-clock differences can be negative (observed down to approximately
-0.6 ms); do not interpret those as negative wakeup latency. The clock split
locates tens/hundreds of milliseconds; it does not promise microsecond
precision or isolate time spent inside the kernel write from GC at that call.

Old-policy replay from ef7e2e8 with collector telemetry, 30 exchanges:
- NORMAL GC: p50 41.6034 / max 197.5651 ms. Exchanges 1, 14 and 26 measured
  197.565, 153.990 and 138.118 ms respectively, with mid-form-fired counters
  0->1, 1->2 and 2->3. Lisp-work median 39.0205 ms; read-call max 1.0009 ms;
  Python send max 0.0133 ms. Write-window max 88.6312 ms occurred in a frame
  whose collector counter advanced.
- Diagnostic GC-disarmed control: zero mid-form-counter increments; no
  distinct collector spike, but median work increased to 101.4801 ms and
  max 112.3338 ms. Disabling collection also changes allocation/reuse behavior
  and is neither a performance fix nor an acceptance result.

New-parser telemetry, 100 exchanges with NORMAL GC:
exchanges 4 and 48 measured 91.0578 and 98.8679 ms, with mid-form-fired
counters 0->1 and 1->2. All other exchanges stayed below 50 ms. These two
slow frames spent 90.9479 and 98.3603 ms in the Lisp-work window. Read-call
max 1.0152 ms and write-window max 1.1086 ms exclude a pipe wake/flush floor.
With boundary AND mid-form collection disarmed in the finite diagnostic only,
there were no counter increments and max roundtrip was 19.4952 ms. Median
roundtrip rose to 13.3753 ms; that control still does not qualify the budget.

Switch 7 alone does NOT disable mid-form collection in this image. A first
control using only switch 7 reproduced the same slow exchange (55) in both
runs. Read-only source inspection explains it: nl_gc_midform_collect checks
its separate enable word and invokes recorded-root collection without the
boundary collector's collect-disabled check. The final causal control calls
both nelisp--debug-switch 7 and 6. No such switch appears in production code.

* Read, write and host framing findings
Real one-byte/no-newline/no-EOF echoes prove read-stdin-bytes 4096 returns a
short available read. It does not wait to accumulate 4096 bytes or require EOF.
Raw byte delivery before newline proves nelisp--write-stdout-bytes is not
line- or block-buffered on the tested anonymous stdout pipe.

Read-only source corroboration, relative to the separate NeLisp checkout
(these references are explanatory; the measurements identify the exact image):
- scripts/nelisp-standalone-build.el, nl_bi_read_stdin_bytes: one
  nl_os_read_stdin call followed by string allocation, no polling loop.
- Windows nl_os_read_stdin / nl_os_read_file_handle: GetStdHandle and one
  synchronous ReadFile; no Sleep, PeekNamedPipe or fill-to-limit loop.
- Windows nl_os_write_stdout: GetStdHandle and one WriteFile; no stdio
  stream buffer, delayed line flush or buffering threshold.
- The string-match wrapper calls the pure Lisp nlre-string-match;
  split-string calls nelisp--split-on-literal. Eight short regexp checks
  reproduce most of the old-policy work without any decision computation.
- windows/host/native_adapter.h, Line: PeekNamedPipe followed by Sleep(1)
  only when empty, then byte reads. This path is absent from the Python-only
  reproducer and cannot cause the independently reproduced 140--218 ms tail.
  No native host pipe change is justified by these measurements.

* Proposed runtime fix (outside this repository; not implemented)
1. Reduce stdlib/evaluator allocation and dispatch overhead for string-search,
   split-string and nlre matching. Compile those helpers through the supported
   Windows bytecode/native closure path or add equivalent bounded fast paths;
   preserve regexp/match-data and string semantics. Use the component matrix
   above to distinguish steady work from collection pauses.
2. Profile nl_gc_midform_collect -> nl_gc_collect_from_recorded_roots ->
   mark/sweep/reclaim on this exact Windows image. Add monotonic phase timings,
   allocation-debt and collection-count telemetry at those boundaries. The
   recorded counter/timestamp correlation localizes the remaining tail to a
   collector invocation, but does not identify its slowest internal phase.
3. Reduce or bound the synchronous collector pause while preserving live
   in-flight roots, conservative/recorded-frame safety, allocation reuse and
   memory bounds. A qualified smaller policy closure or a correctly rooted
   incremental collector is a candidate; simply raising the debt threshold,
   disabling collection or omitting roots is not an acceptable fix.
4. Make the diagnostic collect-disabled control apply consistently to both
   boundary and mid-form entry points, or explicitly document separate switches.
   This improves diagnosis only and is not the production latency remedy.

Acceptance of any runtime fix requires re-running host-windows-s6.py on the
new exact artifact with ordinary GC and unchanged p99<=10/max<=50 ms. The
new image hash, counts, memory, startup and owned cleanup must be recorded.
There is no claim that the proposed runtime work already meets those budgets.
