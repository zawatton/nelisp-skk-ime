* Result and ownership
The current 042f278 follow-up confirms the remaining limit: ordinary HP1
requests allocate about 676 KB in 24,223 native allocator calls, including
reused allocations, and cross a roughly 60.4 MB debt limit every 89--90
requests. These collections are synchronous. Explicit startup collection
before READY removes the initial growth-triggered pause but leaves eleven
collections per 1000 requests. The unchanged IPC budget remains FAIL.
See the final steady-state measurements below; earlier results are historical.

The transport does not have a 150--300 ms fixed floor. On the supplied image,
an unparsed one-byte echo with no newline and no EOF has median 0.0423 ms,
maximum 0.1695 ms. The red HP1 distribution consists of expensive interpreted
string/regexp work plus synchronous mid-form collection pauses. The decision
cond itself is cheap. No NeLisp runtime file was modified.

* Clock split and causal collector control
The diagnostic records float-time immediately before read, after read,
before response write and after write. Python records time.time at send and
raw os.read arrival, plus perf_counter for roundtrip and send durations.
Python does not wait for a newline: it consumes the known response byte count.
The timing record is emitted AFTER the response and is excluded from response
roundtrip. Its cost can affect the next read-wakeup interval, so raw echo and
uninstrumented host-windows-s6.py remain the transport/budget references.

This image's float-time has approximately millisecond granularity. Sub-ms
cross-clock differences can be negative (observed down to approximately
-0.6 ms); do not interpret those as negative wakeup latency. The clock split
locates tens/hundreds of milliseconds; it does not promise microsecond
precision or isolate time spent inside the kernel write from GC at that call.

* Read, write and host framing findings
Real one-byte/no-newline/no-EOF echoes prove read-stdin-bytes 4096 returns a
short available read. It does not wait to accumulate 4096 bytes or require EOF.
Raw byte delivery before newline proves nelisp--write-stdout-bytes is not
line- or block-buffered on the tested anonymous stdout pipe.

Read-only source corroboration, relative to the separate NeLisp checkout
(these references are explanatory; the measurements identify the exact image):
- scripts/nelisp-standalone-build.el, nl_bi_read_stdin_bytes: one
  nl_os_read_stdin call followed by string allocation, no polling loop.
- Windows nl_os_read_stdin / nl_os_read_file_handle: GetStdHandle and one
  synchronous ReadFile; no Sleep, PeekNamedPipe or fill-to-limit loop.
- Windows nl_os_write_stdout: GetStdHandle and one WriteFile; no stdio
  stream buffer, delayed line flush or buffering threshold.
- The string-match wrapper calls the pure Lisp nlre-string-match;
  split-string calls nelisp--split-on-literal. Eight short regexp checks
  reproduce most of the old-policy work without any decision computation.
- windows/host/native_adapter.h, Line: PeekNamedPipe followed by Sleep(1)
  only when empty, then byte reads. This path is absent from the Python-only
  reproducer and cannot cause the independently reproduced 140--218 ms tail.
  No native host pipe change is justified by these measurements.

* Proposed runtime fix (outside this repository; not implemented)
1. Reduce stdlib/evaluator allocation and dispatch overhead for string-search,
   split-string and nlre matching. Compile those helpers through the supported
   Windows bytecode/native closure path or add equivalent bounded fast paths;
   preserve regexp/match-data and string semantics. Use the component matrix
   above to distinguish steady work from collection pauses.
2. Profile nl_gc_midform_collect -> nl_gc_collect_from_recorded_roots ->
   mark/sweep/reclaim on this exact Windows image. Add monotonic phase timings,
   allocation-debt and collection-count telemetry at those boundaries. The
   recorded counter/timestamp correlation localizes the remaining tail to a
   collector invocation, but does not identify its slowest internal phase.
3. Reduce or bound the synchronous collector pause while preserving live
   in-flight roots, conservative/recorded-frame safety, allocation reuse and
   memory bounds. A qualified smaller policy closure or a correctly rooted
   incremental collector is a candidate; simply raising the debt threshold,
   disabling collection or omitting roots is not an acceptable fix.
4. Make the diagnostic collect-disabled control apply consistently to both
   boundary and mid-form entry points, or explicitly document separate switches.
   This improves diagnosis only and is not the production latency remedy.

Acceptance of any runtime fix requires re-running host-windows-s6.py on the
new exact artifact with ordinary GC and unchanged p99<=10/max<=50 ms. The
new image hash, counts, memory, startup and owned cleanup must be recorded.
There is no claim that the proposed runtime work already meets those budgets.

** Measurement method
diagnose-policy-gc.py uses ReadProcessMemory on its own suspended-launched,
job-owned process. It never writes remote memory. The exact image hash above
is mandatory: changed images fail before launch rather than interpreting an
unqualified memory layout. PE .data bounds, actual module base, the arena-base
pointer and runtime invariants validate the native counter addresses.
The native nl_gc_stats layout read is debt, limit, last-sweep live bytes,
collection count, prior allocation total, floor override, percentage override.
Total allocated bytes are prior total plus current debt; this counts allocator
reuse as well as bumps. nl_alloc_diag supplies bucket/linear/bump call counts;
debug-switch 24 enables/reset these counters only. nl_gc_loop_ctx supplies
mid-form count, collection-in-progress and growth watermark.
No switches that disable collection, change limits or change reuse are used.

Counter reads occur outside Lisp, so they do not allocate telemetry lists,
format strings or timestamps in the policy loop. A settled measurement waits
for the runtime to block again after each response and attributes the next
read-buffer allocation to that cycle. Snapshots reject the transient zero-live
state while a sweep recounts live bytes. Floor/percentage overrides must stay
zero; collection must stay enabled; the observed limit must equal
max(16 MiB, 3 * live). This verifies the actual running collector configuration.

Settling can include a collection AFTER a reply. Such a pause is excluded
from that response's roundtrip but included between native-counter timestamps;
it must not be called a budget improvement. In the final settled run, request
361 replied in 8.20 ms but the native snapshot cycle took 89.55 ms and the
collection count advanced. Therefore a separate --continuous mode reads no
per-request counters and inserts no settling waits: it sends the next request
immediately, reads total counters only before/after the 1000 exchanges, and
measures uninterrupted IPC. The unmodified host-windows-s6.py remains the
authoritative budget gate. Explicit-GC scaling probes additionally record
float-time immediately before/after garbage-collect inside Lisp.

** Trigger, startup and time control
Without explicit startup GC, the first settled native snapshot showed:
collections=1, debt=57,016,400, limit=31,640,832, live=10,546,944 bytes and
reserved=64 MiB. The runtime postpones debt-triggered collection while the
collection count is below two. Request 7 crossed the growth watermark by
growing reserved storage to 128 MiB, collected and enabled ordinary debt
triggering. After that, last-sweep live stayed near 20.14 MB and the limit near
60.43 MB. Collections occurred at requests:
7, 99, 188, 278, 367, 457, 546, 635, 725, 814, 904 and 993.
After the first collection, reserved storage stayed exactly 128 MiB while
collections continued. Before each, debt approached the unchanged limit and
after each it reset. This is recurring allocation debt, not repeated growth.

An early startup-GC variant cleared the debt, deferred its first request
collection to 92, kept reserved storage at 64 MiB throughout and still collected
eleven times. The final after-buffer-initialization GC left initial debt only
6,968 bytes, collections=2, live=20,138,128 and limit=60,414,384. Its settled
collections occurred at 93, 183, 272, 361, 451, 540, 630, 719, 809, 898 and 987.
Final live=20,151,512; final reserved remained 64 MiB. There is a startup
residual, but clearing it cannot remove the roughly 676 KB/request churn.

A separate control inserted two seconds of idle before each of ten requests
after startup GC: twenty seconds elapsed, collection count advanced zero
times, and ordinary allocation traffic matched the short-qid baseline. Thus
elapsed wall time alone did not trigger collections within this control.
Read-only native source corroborates a growth-or-debt test at while backedges,
not a timer test. Neither collector thresholds nor GC enable flags were changed.

** Live heap and pause scaling
Private memory is NOT last-sweep live memory. The policy's approximately
145--154 MB private footprint has only about 20.1 MB of traced live arena
objects. Three independent five-explicit-collection probes retained additional
ASCII storage, then measured actual native live/reserved values and Lisp GC
timestamps. Report the measured live size rather than assuming it equals the
nominal padding: conservative retention/runtime storage can make them differ.

| Nominal pad | Final native live bytes | Reserved bytes | Private bytes | GC p50 ms | GC max ms |
|-------------+-------------------------+----------------+---------------+-----------+-----------|
|       0 MiB |              19,937,576 |     67,108,864 |   143,183,872 |     71.30 |     77.17 |
|      16 MiB |              36,715,616 |    134,217,728 |   194,387,968 |     80.44 |     84.01 |
|      32 MiB |              87,047,176 |    167,837,696 |   245,620,736 |     86.01 |     89.11 |

Each probe explicitly collected five times. The 16/32 MiB probes additionally

make recurring synchronous collection sufficiently short.
