#+TITLE: Local-first DDSKK conversion: design and LF1 measurements
#+DATE: 2026-10-06

* Decision and scope
The TSF core should own ordinary conversion: reading construction, dictionary
lookup, ordered candidate traversal, cancel and document commit. It reads an
immutable shared memory-mapped dictionary generation and a small user overlay.
No ordinary conversion or subsequent key waits for the engine. NeLisp DDSKK
remains an asynchronous learning/registration/advanced-feature service. Emacs
is an optional inline display consumer, never a required engine process.

LF1 changes only this design, the S1 ledger and windows/proto. The prototype
is not connected to windows/CMakeLists.txt or any DLL. It establishes lookup
cost, not DDSKK state-machine equivalence or the S2.3 <=30 ms target.

* Evidence from the current implementation

* Search source split
Stock skk-search-prog-list in vendor/ddskk/skk-vars.el:438 contains the
following sources in order. The core must carry an explicit source plan,
not assume every installation has only one large dictionary.

| Stock source | Proposed ownership and requirement |
|--------------+------------------------------------|
| skk-search-kakutei-jisyo-file | Local indexed file; preserve its special immediate-confirm semantics, initially engine until oracle passes |
| skk-tankan-search wrapping large jisyo | Engine: radical/stroke/special @ search |
| skk-search-jisyo-file initial jisyo | Local optional indexed tier in configured order |
| skk-search-jisyo-file personal jisyo | Local overlay; engine is the sole persistent writer |
| skk-okuri-search | Engine initially; auto-okuri is more than exact key lookup |
| skk-search-cdb-jisyo | Builder can import CDB as a typed tier; engine until importer parity exists |
| skk-search-jisyo-file large jisyo | Local shared mmap tier |
| skk-search-server aux large jisyo | Local imported snapshot where available; remote/network-only sources asynchronous, engine fallback when required |
| skk-search-ja-dic-maybe | Engine until compatible adapter exists |
| skk-search-extra-jisyo-files | Local indexed files, preserving their concatenation and filtering behavior |
| skk-search-katakana-maybe | Local generated terminal tier after dictionaries, enabled only by matching setting |
| skk-search-sagyo-henkaku-maybe | Engine initially; special conjugation |
| skk-search-itaiji | Local indexed special tier after matching its single-character guard |

The current engine replaces this entire default list with
ddskk-user-jisyo-search then ddskk-engine-server-search; optionally
skk-search-katakana-maybe is appended. The host shared tier merges configured
DictionaryFiles in first-occurrence order, then can relay to a configured
server. These current supported sources are the initial local scope.
Uninstalled stock features must not be advertised as supported already.
Alternate numbered search lists and arbitrary Lisp search/end hooks require
the engine unless the exported configuration explicitly certifies a local
equivalent. A finite capability digest selects the path before conversion.

** Candidate order, identity and laziness
skk-search stops at the first nonempty source and advances
skk-current-search-prog-list. skk-henkan-1 asks further sources only when
necessary, unioning results with skk-nunion. Therefore a flattened eager
union can be cached internally, but the visible frontier and source exhaustion
must remain DDSKK-equivalent, including when the candidate menu opens.
Space/next/previous/page/select and Enter operate entirely on the pinned
local candidate state. Exhaustion starts registration only after all enabled
sources are actually exhausted; an unavailable source is not a miss.

Store raw candidate identity, displayed word and annotation separately.
DDSKK union uses equal on the full values; the current host shared merge
deduplicates the word before ';' while preserving the first annotation.
These are different policies at different boundaries. Preserve them explicitly
in the current-engine compatibility plan; use stock DDSKK as the final oracle,
and document any deliberately corrected current-engine difference.
Do not insert ';annotation' into the document. Lisp-expression candidates,
ignored-word expressions and hooks are engine features; never evaluate them
as native code or display their source as an ordinary word.

* Okuri, modes and input behavior
** Okuri-nasi and okuri-ari
An okuri-nasi key is the completed reading. An okuri-ari key combines the
hiragana stem and roman okuri discriminator, e.g. KaKu -> かk with resolved
okuri く. The uppercase boundary and rule tree, not a guessed last byte,
determine that key; ASCII abbrev readings must carry a separate mode flag.
Do not normalize kana, punctuation or Unicode beyond DDSKK's actual rules.
Retain stem, okuri letter, resolved okuri, pending prefix, raw input and
editing/cancel policy independently. Complete okuri can trigger conversion
without Space; another Space advances candidates rather than reconverting.

SKK entries retain plain fields and each [okuri/candidates/] block.
Stock skk-select-words-from-list returns only matching-block candidates
when skk-henkan-okuri-strictly is true; with strict-okuri-precedence it unions
matching candidates before plain ones; otherwise it returns plain candidates.
Missing blocks, cancellation retaining/deleting okuri, Backspace inside an
unresolved okuri prefix and automatic conversion must all follow the oracle.
Current host MergeBuiltinCandidates and user --plain-candidates discard
blocks. Consequently today's strict toggle cannot reproduce stock block
ranking. The future index preserves blocks; LF1 raw views already preserve
them, but its PlainCandidates intentionally does not implement ranking.
This discrepancy must be fixed in coordinated engine learning/export too,
otherwise later compaction would erase locally preserved ranking.

** Numeric conversion
Stock skk-num-compute-henkan-key normalizes fullwidth digits, strips grouping
commas and replaces numeric runs (optionally decimal runs) with '#', keeping
the original numeric list. skk-search can union exact and numeric searches
for numeric-enabled programs. Candidate templates support #0 unchanged,
#1 fullwidth, #2 digitwise kanji, #3 positional kanji, #4 dictionary relookup,
#5 financial kanji, #8 grouping and #9 shogi. Template/raw identity is distinct
from displayed expansion. Numeric learning can use the normalized template
key; #4 also has numeric-key update semantics (skk-num-update-jisyo).
Implement pure expansions locally only after stock-oracle coverage, retaining
leading zeros, multiple runs, decimals, large numbers and annotation behavior.
Initially route numeric features, recursive #4 and expression candidates to
the engine. An exact mmap lookup is not numeric conversion support.

** Abbrev, katakana and rules
Abbrev starts with '/' and uses the abbrev keymap; lookup must retain the
literal ASCII key and mode (case, digits and punctuation included). It must
not accidentally romaji-convert or classify Latin keys as okuri stems.
Ordinary katakana mode and q toggles stay in RealtimeFrontend. Katakana
candidate generation is a distinct last search source, gated by the setting;
it must not preempt an existing dictionary candidate.
Use the engine-exported rule tree/profile and settings digest. Preserve n,
nn, n', carry/remainder, doubled consonants, punctuation, z sequences and
custom rules. Persist a last-known verified export so ordinary typing and
conversion work without a running engine. Unknown rule/profile digests route
unsupported commands explicitly; do not silently substitute default romaji.

** Registration
Empty confirmed search or candidate exhaustion opens the engine registration
editor. Send one explicit handover containing session/context epoch, reading,
mode, okuri, raw input, candidate frontier and selected identity. The future
protocol needs state import; today's ConvertKeys replay is a compatibility
fallback, not an asynchronous learning operation. Registration remains modal
and can nest; cancellation restores the pre-registration reading/candidate
checkpoint. Registration commit returns a validated candidate plus a learning
delta, updates the local overlay and commits once. New local conversions need
not await unrelated registration or learning in another application.

* Shared index and publication
** Proposed production format (not yet implemented)
Use fixed-width little-endian offsets, never process pointers, with magic,
schema, file length, generation, source/config/rule digests, source content
hashes, checksum and build completion marker. Sorted UTF-8 key table points
to source-specific candidate vectors and a string pool. Candidate records
retain raw word/template, annotation, source rank, flags and typed okuri-block
vectors. Keep user ranking as its own generation/overlay; do not bake its
priority into an unchangeable shared list. Reject unknown versions, overflow,
out-of-bounds/overlapping sections, malformed UTF-8 and incomplete publication.
Builder parses source files off the keystroke thread. Record bad-line counts;
never silently treat a missing dictionary as an empty successful generation.

Build a new uniquely named file, flush, validate, then atomically publish a
small manifest. Readers open read-only with delete sharing, pin the mapping
for a composition, and map the next generation only at a safe boundary.
Old mappings remain valid until their final reader releases them. No in-place
editing under readers; cap generation retention and validate file access
permissions. Mapped pages are shared through the OS cache across app processes.
Measure private bytes separately from mapped bytes and working set.

** LF1 experimental format
windows/proto/mmap_index.h defines a 32-byte header (magic/version/count/size),
48-byte sorted record (offset/length pairs for key/user/shared) and UTF-8 raw
payload. Read-only CreateFileMappingW/MapViewOfFile, binary search, zero-copy
Hit views; caller must retain Index lifetime. Open validates header, bounds
and strict key order. Build preserves raw annotations/blocks and duplicate
key last-wins behavior. PlainCandidates drops block fields and exact-unions
user before shared. It handles one shared source only; no checksum, content
digest, UTF-8 validator, durability/manifest publisher or ranking protocol.
It is not a distributable dictionary or production-safe index format.

* Learning and cross-process consistency
Stock skk-update-jisyo-original moves the confirmed word to the front, updates
matching okuri ranking blocks and history, handles numeric template keys,
and records shared-personal updates. Purging a shared word can install an
ignored-word expression; merely deleting the local word does not suppress
the shared result. Current ddskk-user-jisyo--update is narrower: cleans the
full candidate, exact-equal move-to-front by skk-henkan-key, append of the
whole changed entry to .journal; purge removes it and immediately flushes;
compaction writes the base before truncating the journal. It drops okuri
blocks on load. Existing journal behavior is useful, but not a stock-parity
specification. The design must migrate storage/export with explicit schema
and stock-oracle tests for okuri, purge tombstones and numeric learning.

Document commit is immediate in the core. Add a pending in-memory learning
delta so a second conversion in that same client sees its just-confirmed
word first. Enqueue LEARN(session, epoch, unique operation id, generation,
key, okuri, raw candidate/template, display word, action). The engine is the
single writer and orders operations globally, journals them durably, then
ACKs with an authoritative sequence and changed-entry delta. At-least-once
delivery must be idempotent; the acknowledged operation-id watermark must
survive restart. Never infer confirmation by candidate index alone.

Publish the new overlay to all clients; fold pending deltas over the confirmed
generation until their ids are acknowledged. Concurrent same-key learning
uses engine sequence order. Purges and registration are explicit operations.
A composition pins its candidate list even when another app learns a word;
apply new ranks on the next conversion. Late ACKs cannot rewrite committed
text, move a selection or revive an expired context. Engine failure leaves
ordinary input usable; bounded queued learning and an explicit unsaved status
avoid claiming durability that did not occur. A protected local spool is
needed for crash-safe pending learning; implement it off the TSF thread.

The engine must not maintain a shadow local-key stream and later replay it
one key at a time. Supported local conversions own their complete state.
Engine calls for unsupported commands use an explicit epoch-tagged handover
barrier. A late fallback response applies only to that barrier's live context.
Engine responses/learning ACKs carry no authority over a newer local session.

* Document and inline channels
Produce one core state snapshot for candidate UI and document edits. Obtain
the TSF edit session to replace the reading/okuri range and commit synchronously
when permitted; preserve existing edit-session failure handling and caret
identity. New keys update local state directly, without provider waiting and
per-key replay. Closing/switching context invalidates UI epochs and callbacks.
InlinePreedit already publishes snapshots on its own socket worker with epochs.
Use the same local state there; inline socket/listener delay cannot block input.
Candidate caret placement and Emacs rendering are presentation consumers.
Missing/wrong/disconnected listeners retain existing TSF fallback behavior.

* Failure policy and rollout
- Missing/corrupt index: keep last verified generation; otherwise explicitly
  choose the existing private-engine path before displaying a candidate.
- Not-yet-built/user-overlay-not-ready: do not claim a dictionary miss or
  open registration; keep the reading and offer fallback/unavailable status.
- Engine down: local ordinary conversion and commits work; learning is
  pending, registration/unsupported commands report unavailable.
- Unknown hooks, numeric/expressions/advanced sources: select engine ownership
  before conversion; timeout/cancel leaves editable reading, never duplicates
  a document commit. Remote-source replies cannot reorder visible candidates.
- Resource limits: no file build, full mapping validation, network access,
  unbounded candidate expansion or journal compaction in a key callback.
- Rollout: S1 prototype -> private ordinary-conversion oracle -> okuri/modes
  -> asynchronous learning/registration -> private TSF and real Emacs inline
  latency/typing-ahead gates -> opt-in production setting -> user-approved live
  deployment. LF1 does not create settings, deploy or register anything.
